What it does

Sandboxes, policy and plumbing — handled.

Running an agent stack is normally forty commands, six config files and a firewall written by hand. Nestbox reduces it to one boot, one web UI and one API, without giving up the isolation that makes agents safe to run at all. The roadmap tracks what ships in which phase.

  • 01

    Nests on demand

    Create a sandbox for Claude Code, Hermes Agent, OpenCode, OpenClaw or a custom stack in one click. Start it, stop it, exec in, stream logs, delete it.

  • 02

    The AI firewall

    Filesystem, Landlock and process policy are fixed when a nest is created. Network rules are live: change a rule, it applies to the running sandbox, and you can roll it back.

    See the policy model →
  • 03

    Reachable without port forwarding

    Every nest gets a hostname and a valid certificate through the traffic container and the WireGuard overlay. No tunnels to babysit, no open ports to remember.

  • 04

    Backup and restore

    Snapshot the controller, gateway, policies, certificates and nest workspaces. Restore the lot, or pull back a single file, from the browser.

  • 05

    One API behind every button

    The UI is a client of the same versioned HTTP API you get: token or session auth, admin, operator and viewer roles, stable error codes, Server-Sent Events.

  • 06

    Agent packs, not setup guides

    Choose a pack and get the nest, provider profile and policy set that make it work. First-party packs cover the common stacks; a custom stack is a pack too.

The AI firewall

Agent traffic, on a short leash.

A sandbox without a network policy is a machine with your API keys and an open route to anywhere. Nestbox gives every nest a policy document — and one place to change it.

Each nest carries four policy sections: filesystem, Landlock, process and network. They read as one firewall in the UI, and only the network section can hot-reload into a running sandbox. The other boundaries cannot move under a live process — so the UI says so instead of pretending otherwise.

  • Only the binaries you name may use an endpoint. A shell script that calls curl is not that binary, so it is not allowed.
  • Enforced blocks. Audit records and allows. Shape a rule against real traffic before you tighten it.
  • Every change is diffable. Compare against the policy the gateway is enforcing, apply, and roll back if the nest disagrees.

    Edit

    Structured form or raw YAML.

  2. 02

    Validate

    Checked against the schema first.

  3. 03

    Compared with the effective policy.

  4. 04

Four ways to run it

Same appliance. Four shapes of hardware.

One image covers a cloud GPU, a plain Ubuntu box, a machine with a local GPU and a laptop that only serves the model. Between them, only the provider profile moves — nests, policies and the API stay the same.

  1. 01 Cloud

    Cloud GPU VM

    Boot the image on a GPU instance and open the UI. No local hardware to buy, no driver stack to assemble, and the model stays next to the work.

    You need A GPU instance and the ISO.

  2. 02 CPU only

    Local box, no GPU

    Run the control plane on any Ubuntu machine and point nests at cloud models. Evaluate the workflow before spending on hardware; the policy model is identical.

    You need Any Ubuntu host, cloud model access.

  3. 03 Local GPU

    Local box, with GPU

    Attach the GPU to a local-nemotron nest. The pack runs vLLM and the provider profile points at localhost; the firewall stays in front of the traffic.

    You need A supported GPU and enough VRAM.

  4. 04 Overlay

    Laptop hosts the model

    Keep the appliance in the cloud and serve the model from your laptop over WireGuard. The endpoint moves to the overlay; the nest policy does not.

    You need WireGuard reachability and a model endpoint.

↔ Moving between these four changes a provider profile, not a workflow. Start without a GPU if that is what you have.

Nemotron

Local models, one family.

Only Nemotron ships as the first-party local model. One family means one set of provider profiles, one set of policy profiles and one thing to test. Cloud models remain available through any OpenAI-compatible endpoint.

API

One API behind every button.

Everything you can click is an HTTP call with a stable contract: token or session authentication, admin, operator and viewer roles, one error envelope and Server-Sent Events for live state. The schema is frozen in CI.
